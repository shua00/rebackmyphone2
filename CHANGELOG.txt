v1.5 — 2026-10-29 · 红米 Android 15 定位与 WiFi 扫描修复
================================================================================

【新增】AndroidManifest.xml
--------------------------------------------------------------------------------
- 加 NEARBY_WIFI_DEVICES 权限（带 neverForLocation 标志）
    原因：Android 13（API 33）引入该权限，专门管控「扫描周围 WiFi」。
          没有它，targetSdk 34 的 App 在 Android 13+ 上 startScan() 永远返回 false
          或空结果，即使有 ACCESS_FINE_LOCATION 也不行。
          红米 Android 15 上「周围热点」功能因此完全失效（日志里全是
          "startScan 返回 false" 或 "扫描完成: 0 个热点"）。
          中兴 Android 11 不受影响，所以两台设备对比才看出差异。

【修复】DeviceInfoUtils.java
--------------------------------------------------------------------------------
- scanNearbyWifi 重写
    · startScan 返回 false 时降级读 getScanResults() 缓存
      （覆盖「缺权限 / 后台节流 / 频率限制」三种场景，不再空手而归）
    · 扫描结果 0 个时日志区分「后台限制」和「附近无热点」
    · 新增辅助方法 buildResultFromScanResults(Context, List<ScanResult>, String)
      把 List<ScanResult> 转成按信号强度降序的 JSONObject 列表，供「正常扫描」
      和「缓存降级」复用
- 移除 isScanThrottled() 检查
    原因：该方法在部分 SDK 中被标记为 @hide，普通 App 在 compileSdk 34 下
          编译报 "cannot find symbol"。startScan 失败后的降级读缓存已经覆盖
          「被限流」场景，删掉不影响功能，且跨版本兼容。

【修复】TrackingService.java · requestSingleLocationAndReport
--------------------------------------------------------------------------------
- 超时 10s → 60s
    原因：GPS 冷启动 TTFF 通常 30–60 秒（室内可能更久）。原来 10 秒就放弃，
          上报的是 lastLocation（可能几小时前的旧坐标）或 null。
          红米室内用 GPSTest 都难拿到定位，App 10 秒更拿不到。
          60 秒给 GPS 冷启动留足时间，拿到第一个 fix 立即上报，不等满 60 秒。
- 去掉 isProviderEnabled(NETWORK_PROVIDER) 硬判断，无条件 try-request
    原因：Android 15 上 isProviderEnabled(NETWORK_PROVIDER) 语义变了——
          它判断的是「用户是否在设置里启用了 WiFi 扫描用于定位」，
          而不是「network provider 能不能用」。红米关掉了 WiFi 扫描，
          所以 isProviderEnabled 返回 false，导致 App 根本不请求 NETWORK provider，
          而 NETWORK 恰恰是室内唯一能用的定位方式。
          改成 try-request 后，室内 GPS 拿不到时 NETWORK 仍能工作。
- 新增日志：「已请求 NETWORK/GPS provider（单次）」「单次定位成功: provider=xx」
- 60 秒超时日志：记录 lastLocation 是否有值，便于判断「真无定位」vs「用了旧值」

【修复】TrackingService.java · startLocationUpdates
--------------------------------------------------------------------------------
- 去掉 isProviderEnabled(NETWORK_PROVIDER) 硬判断，无条件 try-request
    原因：同上。持续监听的 NETWORK 更新被挡住，导致 lastLocation 长期不更新
          （室内 GPS 不更新，NETWORK 又不注册，lastLocation 一直是最旧值）。
- 日志文案：NETWORK=off 改成 NETWORK=设置未启用(可能仍可用)
    原因：避免误导。Android 15 上这个状态不代表 provider 不可用。

【修复】TrackingService.java · 自检块
--------------------------------------------------------------------------------
- 定位 provider 文案同步改为「设置未启用(可能仍可用)」
    跟 startLocationUpdates 的日志保持一致，避免排查时被 off 误导。

【本轮未改但已确认】
--------------------------------------------------------------------------------
- 中兴夜间断档 2–6 小时：是 Doze 深度冻结，不是 force-stop
    证据：进程计数连续（457→599→831 分钟），屏幕亮起自动恢复，
          无 onCreate 重新触发。跟 force-stop（计数重置、必须手动打开）不同。
    结论：中兴 MyOS 的 Doze 比原生激进，代码层无解。
          根治只能手动关中兴「深度睡眠 / 智能省电」或长期插充电器
          （充电时 Doze 永不触发）。
- 6 小时心跳延迟 45–60 分钟：Doze 合并 setAndAllowWhileIdle
    影响：在 force-stop 场景下 6 小时心跳本来就没用，延迟 1 小时不影响功能。
    结论：不改。
- 红米电量卡 1% 7 小时：电池老化/校准异常，非 App 问题。
- 红米内存 GC 前峰值 26MB（maxMemory 256MB，占 10%）：正常，继续观察。
- WiFi 扫描夜间全部失败：Android 9+ 后台限流，系统级限制，无法绕过。

【验证】
--------------------------------------------------------------------------------
- GitHub Actions 编译通过（缓存服务临时故障的 Warning 无害）
- 待装机验证：
  · 红米 WiFi 扫描：ACTION_SCAN_WIFI 后日志应出现「扫描完成: N 个热点」（N > 0）
  · 红米室内定位：ACTION_LOCATE_ONCE 后 60 秒内应出现「单次定位成功: provider=network」
  · 自检块：「定位 provider: GPS=on, NETWORK=设置未启用(可能仍可用)」

【未解决】
--------------------------------------------------------------------------------
- 中兴 A2023BH 夜间 Doze 冻结 2–6 小时
    原因：MyOS 11.5.8（Android 11 + 2022-10-01 补丁）的 Doze 实现比原生激进，
          夜间会暂停 App 的 CPU 时间片，连 setExactAndAllowWhileIdle 都不给。
          进程一直活着（心跳计数连续），屏幕亮起自动恢复。
    结论：代码层无解。根治只能：
          1. 手动关中兴「设置 → 电池 → 应用耗电管理 → 不限制」
             + 「手机管家 → 自启动管理 → 允许」
             + 「设置 → 电池 → 更多电池设置 → 关闭智能省电/深度睡眠」
          2. 备用机长期插充电器（充电时 Doze 永不触发，最省心）
- 中兴 force-stop（跟 Doze 冻结不同）
    原因：stopped=true 后静态广播全部失效
    结论：只能 ADB 或用户手动打开 App，C 方案暗号也救不了
- 红米电量卡 1% 7 小时：电池老化/校准异常，建议校准或换电池

【观察中】
--------------------------------------------------------------------------------
- 红米内存 GC 前峰值 26MB：正常波动，如 24h 后涨到 50MB+ 再查泄漏
- 6 小时心跳延迟 45–60 分钟：Doze 合并，不影响功能，不改
- WiFi 扫描夜间失败：Android 9+ 后台限流，系统级限制
- 上报耗时偶尔 15–19 秒：接近超时边界，频率低（17h 2 次），不改

    FIND_ME_UPLOAD_LOG / FIND_ME_LOCATE_ONCE / FIND_ME_SCAN_WIFI /
    FIND_ME_RESTART_UDP / FIND_ME_TEST_LOW_BATTERY

v1.2 — 2026-10-28 中午 · 502 根因修复
================================================================================

【修复】server2.py · 502 根因
--------------------------------------------------------------------------------
- 问题：旧代码 recv(16384) 只读一次，TCP 分段时 body 不完整
        → json.loads 失败 → except 只 print 不回响应
        → Cloudflare 判 502
- 修复：
    1. 按 Content-Length 循环 recv(65536) 读完整 body
    2. 所有 except 分支补 sendall(500) + Connection: close
    3. 所有响应加 Connection: close
    4. 分支判断改用 header_text（避免 body 里的路径字符串误判）
- 验证：
    · 本地非法 JSON → HTTP 500（不再是 curl: (52) Empty reply）
    · 本地合法大 JSON（12.5KB / 200 个热点）→ HTTP 200
    · 公网域名非法 JSON → HTTP 500
    · 12:21 部署后，两台设备零 502

【修复】server2.py · KeyError
--------------------------------------------------------------------------------
- 问题：新设备首次上报带 cloud_logs 时
        ALL_DEVICES_STATUS[dev_id] 不存在 → KeyError
- 修复：先 if dev_id not in ALL_DEVICES_STATUS: ALL_DEVICES_STATUS[dev_id] = {}
        再合并 cloud_logs

【变更】server2.py
--------------------------------------------------------------------------------
- init_db() 加 timeout=10 + PRAGMA journal_mode=WAL（防并发写丢数据）
- 所有 sqlite3.connect() 加 timeout=10
- udp_listener 的 except OSError 判断 errno 98/10048，
  明确提示 8888 被 chat.py 占用
- allDevicesData = json.dumps(...).replace('</', '<\\/')
  （防 WiFi SSID 含 </script> 破坏页面）
- smart_send 用 list(ALL_DEVICES_STATUS.items()) 快照（防并发 RuntimeError）
- format_loc_time 的 except: 收窄为 except Exception:
